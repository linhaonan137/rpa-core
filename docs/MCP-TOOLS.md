# MCP 工具层：粒度设计、参数约定、已知缺陷

> 本文只写**决策与理由**，不写会变的数字。
> 工具总数、节点总数、工具名清单，一律以 `api/mcp.py` 里 `@mcp.tool` 的实际注册为准（`list_node_types` 可查节点）。

## 1. 为什么不做"一个节点一个工具"

单个 MCP 工具的 schema 约 250~400 token。工具数线性涨，上下文线性吃。

| 工具数 | 常驻上下文 | 后果 |
|---|---|---|
| 20 上下 | ~5k token | 无感 |
| 200 | 50k~80k token | 吃掉一半以上窗口 |
| 200+ | 同上 | 模型在长列表里的选择准确率显著下降，选错工具 = 跑错流程 |

**工具越多，Agent 越笨。** 这是上下文预算与选择准确率的双重约束，不是审美偏好。

## 2. 三层结构

```
L1  流程级开关      flow_read / flow_run / run_status        ← 一整个流程的起停
L2  意图级工具      web_fill / element_pick / file_ops ...   ← 一个工具 = 一个意图
L3  节点（不暴露）  藏在 L2 内部                              ← 实现细节
```

Agent 只看得到 L1+L2。节点是实现细节，不注册成工具。

## 3. 三条设计原则

1. **按意图聚合，不按实现镜像**
   `web_fill` 一个工具覆盖输入框、下拉框、复选框、上传文件——因为它们对 Agent 是同一个意图："把这个表单填上"。不拆成四个工具。

2. **参数用 `action` / `kind` 分流，不用工具分裂**
   `file_ops(action="copy" | "move" | "delete")` 而不是三个工具。别名要双向兼容（`action` 与 `kind` 都收，历史调用两套都有）。

3. **必须有逃生舱**
   `script_run` 一条工具覆盖长尾 + 无限扩展。**覆盖高频之后，剩下的不要为它做工具**——加工具的成本是永久的上下文开销，而 `script_run` 三行能解决的就不该占一个工具位。

   判断标准：想加工具时先问"能不能用 `script_run` 三行解决"。能就别加。

## 4. 参数分三类，只有第一类该由 Agent 填

| 类型 | 例子 | 有默认吗 | 谁填 |
|---|---|---|---|
| **语义必需** | 选择器 / URL / 文本 / 元素 key | 无 | Agent 第一轮 |
| **调优类** | `limit_ms` / 重试次数 / 等待状态 / 时延 | 有，按动作分档 | 引擎（不填用默认） |
| **断言类** | `expect` / 校验条件 | 默认无 | 人 / Agent 第二轮，可选 |

**准确说法不是"Agent 不改参数"，而是"Agent 只填语义必需的，不碰调优的"。**

默认值按动作类型分档（写在引擎里，不给 Agent 看）：

| 动作 | 默认超时 | 默认重试 |
|---|---|---|
| 打开页面 | 60s | 1 |
| 点击 / 输入 | 30s | 2（退避 1s、2s）|
| 读取元素 | 15s | 1 |
| 等接口返回 | 30s | 1 |
| 文件 / 数据处理 | 10s | 0 |

## 5. 等待能力的归属

流程里有多种等待节点，但**不能让 Agent 自己决定等多久**。

| 等待类型 | 谁负责 | 暴露给 MCP 吗 |
|---|---|---|
| 点击/输入前"元素可交互" | 引擎中间件内建（三态等待） | 否，工具内部做 |
| 页面加载（load / domcontentloaded） | 节点参数 `until` | 否，写在流程 JSON 里 |
| 等文本出现 / 元素消失 / URL 变化 | `web_wait` | 是 |
| 等某个接口返回 | `web_network` | 是 |
| 固定 `sleep N 秒` | `sleep` 节点 | **默认不暴露** |

**为什么固定 sleep 不给 Agent**：模型最容易犯的错就是"睡一下应该就好了"。固定 sleep 快了失败、慢了浪费，还会掩盖真实问题（该等条件却在等时间）。确实需要固定间隔（给服务端节流）时，由人写在流程 JSON 里。

## 6. 工具分组

按意图分五组：

| 组 | 代表工具 | 说明 |
|---|---|---|
| 网页与元素 | `web_open` / `web_click` / `web_wait` / `element_pick` / `element_check` | 页面操作 + 元素库闭环（拾取 → 用 → 体检）|
| 通用能力 | `file_ops` / `data_ops` / `script_run` / `ai_call` / `net_http` | 一工具带 `action` 分流 |
| 流程 | `flow_read` / `flow_save` / `flow_patch` / `flow_rollback` / `flow_delete` / `flow_run` | 读、改、回滚、删、跑 |
| 队列 | `flow_run_async` / `flow_task` / `flow_tasks` / `flow_cancel` | 长流程不阻塞调用方 |
| 观测 | `run_status` / `read_failure` / `record_*` | 实例状态、失败现场、录制 |

**分组原则是"真实意图有多少个"，不是"压到多少条"。** 第 1 节约束的是"别把节点镜像成工具"，不是"必须砍到某个数字"。

工具名一律以代码为准：改文档前看 `api/mcp.py` 的 `@mcp.tool`，不要凭记忆或旧稿引用。

## 7. 改流程的入口：`flow_patch`

没有它，调参只能手改 JSON 文件——那是这个工具存在的唯一理由。

三条硬限制：

| 限制 | 原因 |
|---|---|
| 只能改节点的 `args`，不能改 `type` / `id` / `edges` | 结构改动要重新生成整个流程，那是 `flow_save` 的事 |
| `dry_run` 默认 `True` | 改流程是危险操作，先看 diff |
| `reason` 必填 | 审计靠它，每条变更都要能回答"为什么改" |

**参数建议由数据算，不由模型拍。** 每次执行记录节点 `elapsed_ms`，统计该节点 P95：

```
P95 > 超时 × 0.8      → 建议提高
连续 3 次 < 超时 × 0.1 → 建议降低
→ 写进变更流水的 suggestion 字段，不自动改
```

模型没有任何依据知道"这个按钮要等 45 秒"，它只能猜 30 或 60；执行记录里的 P95 是实测值。**没有 suggestion 字段，调参环节就是纯猜。**

`flow_save` 覆盖前必须留快照（与 `flow_patch` 一致），否则改坏了回不去。

## 8. 浏览器实例怎么管

三个漂移是难管的根源：

| 漂移 | 表现 | 后果 |
|---|---|---|
| **端口漂移** | 指纹浏览器每次启动 CDP 端口不同 | 写死端口就连不上 |
| **身份漂移** | 实例里还留着上个流程的 profile | 数据跑到错账号 |
| **僵尸实例** | 后端挂了但浏览器进程还在 | 下次启动抢端口失败 |

实例必须有身份证：`id` / `cdp_url`（从 launch 响应取，不写死）/ `pid` / `profile` / `mode` / `occupied_by` / `lease_until`。

生命周期 `acquire → 用 → release`：

- 有空闲实例：校验 profile 匹配 → 占用 → 返回
- 无空闲：启动或接管 → 从响应取 cdp_url → 记录 → 返回
- 已被占：排队或拒绝
- `release`：关本次新开的页面（保留主页）、清占用、异常退出标 `dirty`（下次 acquire 前先 reset）

**单实例串行是刻意的选择**：并发下"哪个流程在哪个浏览器"变成必须回答的问题，还要处理抢焦点、抢端口、profile 混淆，三倍调试量。日常任务是每日几条流程，不需要并发——这个问题直接消失。

但必须做的事一条不能少：每次执行记录 `run_id → browser_id → cdp_url → profile`（出问题唯一能追溯的线）；执行结束清页面；异常退出标 dirty；失败快照带 `cdp_url`（Agent 能连上去看现场）。

`run_status(flow, limit)` 查最近执行记录与各节点耗时趋势 —— **这是调参的唯一数据依据**，不是"看一眼状态"。它不报浏览器实例：单实例串行 + 队列已让"谁在用"答案唯一，要查占用看 HTTP 的 `/tasks`。

**回滚是改流程的配套出口**：`flow_save` / `flow_patch` / `add_node` / `drop_node` / `move_node` 每次落盘前都写 `.versions/<flow>.snap-N.json`，`flow_rollback` 就是读回这些快照的唯一入口。没有它，快照是只写不读的磁盘垃圾，"改坏了回不去"。回滚本身也拍快照（`pre`），滚错了还能再滚回来。

`flow_delete` 默认保留快照，所以删掉的流程可以用 `flow_rollback` 重建 —— 这也是为什么删除敢做成一个动作而不是"归档"。

## 9. 三类高危缺陷模式

工具层写得再完整，只要底层节点没实现，调用时才炸。这三类是反复出现的模式，加新工具时按这个清单自检：

**① 工具在、能力不在（幽灵节点）**
现象：工具描述说得头头是道，调用返回"未注册的节点类型"。根因是工具层先写完了，节点从未实现，且没有启动自检。
修法：`main()` 启动时检查 `nodes.failures()` 与 `_call_ghost_refs()`（节点名幽灵引用），有失败就往 stderr 报警。**`load_all()` 吞异常是对的（单个模块坏不该拖垮整包），但必须有人看 `failures()`，否则就是静默丢能力。**

**② 静默成功**
现象：参数被丢、返回 `ok:true` 但什么都没做。例：`csv_parse` 丢了 path → 空 CSV 却报成功；`write content=""` 被吞 → 写不了空文件；`flow_read()` 列表缺 `ok` 字段。
判据：**返回成功但没有副作用，比报错危险**。每个工具都要回答"这个成功有证据吗"。

**③ 参数名映射**
MCP 层的参数名与节点 `args` 的键不是同一套，中间靠映射表粘合。漏一条 = 该动作完全不可用，且不报错。审计中出现过 `text/rows → items`、`rows → row`、`dest → name`、`control → target`、`limit_ms → timeout_ms` 等多组。
判据：新增或改动节点参数时，**映射表必须同步改**，且要有一次真调用验证。

另外一条环境教训：`python_script` 曾在事件循环里同步 exec，卡死且无超时；改子进程后解决。深层原因是 `redirect_stdout` 是进程级的，超时后 `__exit__` 不执行 → stdout 泄漏成 StringIO → 所有响应发不出去。**同步 exec 不能放在服务进程的线程里。**

## 10. 仍未修（按影响排序）

| 缺陷 | 原因 / 现状 |
|---|---|
| `web_capture` 对 `data:` URI 失败 | Playwright 限制，需先转存 |
| `web_click` 的 drag 分支 `limit_ms` 不生效 | 内部硬编码超时，`_pick` 之外的 `drag_to` 漏了 |
| 非法枚举只报 pydantic 裸文本，无 `ok:false` | FastMCP 框架层，需要包一层 |
| `notify` 三种 channel 的 body 结构相同 | 钉钉/企微格式本来就接近，属文档说明不足 |
| `file_ops delete` 对不存在的文件返回 ok | 幂等语义，刻意为之，不是 bug |

已修但值得记住的：`flow_run limit_steps` 曾在循环内每轮重置预算（每轮都拿完整预算 → 限步失效），根因是子 Runner 复用了 `max_steps` 而非剩余预算；`flow_run start_at` 指向不存在节点曾抛裸 KeyError 穿透协议层。

## 11. 兜底逻辑（"够用"的真正保障）

```
L2 工具覆盖高频场景
    ↓ 不够用
script_run 写 Python（覆盖剩下全部节点 + 无限扩展）
    ↓ 还不够
net_http 直接打自己的服务
```

三条通路都在，就不需要为低频需求加工具。

## 12. 看页面 / 验证类：按意图选工具

工具多了最大的害处不是 token，是**选错**。下表按意图钉死，别再临时判断：

| 意图 | 工具 | 不要用 |
|---|---|---|
| 第一次进页面，想知道能点什么 | `web_scan` | snapshot / fields |
| 读内容型页面，先理解整体 | `web_snapshot` | read |
| 表单字段（靠 label 区分无 id 的输入框）| `web_fields` | scan |
| 已知元素在哪，要取内容 | `web_read` | dom_inspect |
| 抓重复结构的列表 | `web_extract` | web_read(list) |
| 看元素的真实结构（属性 / 祖先链 / 样式）| `dom_inspect` | web_read |
| 立即查状态（存在 / 可见 / 页面就绪）| `web_check` | web_wait（那是等）|
| 等某个条件成立 | `web_wait` | 固定 sleep |
| 验证一个目标现在还能不能定位（任意选择器）| `web_verify` | element_check（那是批量的）|
| 批量体检元素库 | `element_check` | element_diagnose（那是单条的）|
| 单个元素逐层诊断（决定要不要重拾）| `element_diagnose` | element_check |

### 两个可见性口径，别混

| 口径 | 谁用 | 判据 | 含义 |
|---|---|---|---|
| **可操作可见** | `web_check` / `web_visible` | Playwright `is_visible()` | 能不能点它（不排除 `opacity:0`）|
| **视觉可见** | `web_verify` / `dom_inspect` | 有尺寸 + 非 `hidden` + 非 `opacity:0` | 人眼看得到吗 |

同一个元素两个口径可能给不同答案。**判断"能不能操作"用前者，判断"用户是否看得到"用后者。**

### 三个"验证"为什么不合并

`web_verify`（任意选择器，一对一）、`element_check`（库内 key，批量 + 写 hits/misses）、`element_diagnose`（单条逐层诊断）共享同一条 `resolve_fingerprint` 数据链，但服务三个不同动作：**写流程前试一下 / 定期体检 / 查为什么坏了**。

合并会让其中一个变成带 4 个模式分支的怪物，比三个各司其职更难选对。同理 `web_check` 保留（它的 `page_ready` 分支别人没有）。

**代价**：Agent 需要靠上一张表选路。表比分支好维护。
