# 自愈：分层、判据、变更记录

> 核心原则：**定位问题优先改元素库（一处生效、影响全流程、易回滚），不要一上来就改流程节点。**
> 自愈不走 MCP——同进程直接调内核函数，绕协议是纯开销。

## 1. 五层，风险逐层升高

| 层 | 谁做 | 改什么 | 影响面 | 风险 |
|---|---|---|---|---|
| **L0 运行时自愈** | 引擎，零外部介入 | **什么都不改** | — | 无 |
| **L1 改元素库** | 自愈组件，规则 | 元素库条目 | **所有引用它的节点一起修好** | 低，可秒回滚 |
| **L1.5 诊断** | 探测器（可带 LLM） | 什么都不改，**只出结论** | — | 无 |
| **L2 改流程** | LLM | 节点 / 边 | 单个流程、单点 | 高，难回滚 |
| **L3 报人** | — | — | — | — |

## 2. 每层具体干什么

**L0 运行时自愈**

1. 元素三级定位：`get_by_role(role, name)` → css 兜底 → hints 候选
2. 同名元素挑**可见的那个**
3. 分段滚动找懒渲染元素
4. 重试前先 **reload 页面**（吃掉弹窗/遮罩类失败）
5. 拟人轨迹点击，失败回退原生 click

**L1 改元素库**

三级全失败 = 存下来的信息全过时了，此时重新探测页面（确定性，不调 LLM）：

```
① 按 name（可见文本）找
② 按 aria-label 找
③ 按 placeholder 找
④ 按「邻近文本 + 标签结构」找（父容器内的同位置元素）
⑤ 按「原坐标区域」找（最后手段）
   唯一匹配 → 更新该条目的 role / name / css / hints，打 _heal 标记
   多个匹配 → 加限定（父容器 / 邻近文本）缩小
   一个都没有 → 升 L1.5
```

**为什么必须改元素库而不是改节点**：改一条元素，所有引用它的节点同时修好；改节点只修一个点，别的流程用到同一元素还得再修一遍。

**L1.5 诊断**（L1 修不动时，先搞清楚"为什么"）

| 现象 | 诊断结论 | 下一步 |
|---|---|---|
| 元素存在、唯一，只是属性变了 | 元素库过期 | 回 L1 更新 |
| 元素存在、多个匹配 | 定位歧义 | 加限定后回 L1 |
| 元素存在但不可见 / 被遮挡 | 交互状态问题 | 关弹窗 / 滚动后回 L1 |
| **元素不存在，页面是登录页或验证页** | **会话失效 / 风控** | **L3 报人**（改流程没用）|
| 元素不存在，页面结构大变 | 网站改版 | L2 |
| 元素不存在，多了确认框 / 二次步骤 | 流程缺步 | L2 加节点 |

**这张表是"能不能自愈"的关键**：不做诊断直接上 L2，等于让 LLM 用"改选择器"去解决"登录失效"——越修越乱。

## 3. 修复率从哪来

按 100 次失败拆：

| 层 | 解决 | 累计 |
|---|---|---|
| L0 运行时 | 60~65 | 60~65 |
| L1 改元素库 | 18~22 | **78~87** |
| L1.5 诊断后回 L1 | 3~5 | 81~92 |
| L2 改流程 | 6~8 | **87~100** |
| L3 报人 | 8~13 | — |

**L2（LLM）只贡献 6~8 个百分点，L0+L1 贡献 80 以上。** 把力气花在"三级定位 + 重定位阶梯 + reload"上，比优化 prompt 有效得多。

**六个配套杠杆**：

| # | 手段 | 主要作用层 |
|---|---|---|
| 1 | 候选列表带 role + name + 可见性，按相似度排序 | L0 |
| 2 | 失败后保留浏览器 + 共享 CDP | L1.5 |
| 3 | 按需抓整页 accessibility snapshot | L1.5 / L2 |
| 4 | **错误分类器先判层，再选修法** | 分流 |
| 5 | 补丁作用域最小化：L1 只动元素库，L2 只动单节点 | L1 / L2 |
| 6 | 重试前先 reload | L0 |

## 4. 自愈的 5 步

```
① 失败 → FailureContext（节点 / 参数 / 错误 / 候选 / 快照 / 网络尾巴）
② 分级（见第 1 节）
③ 改之前先落快照 .versions/<flow>.snap-<n>.json（原子写，可秒回滚）
④ 直接改原文件，改动写进两处（见第 5 节）
⑤ 从失败节点断点续跑：
     成功 → 保留改动
     失败 → 回滚快照，升级到 L2 或报人
```

**续跑就是验证**：改完从失败节点续跑，成功则保留、失败则回滚。所以不需要建副本。

**局限**：从 n5 续跑，n1~n4 的副作用（已开的页面、已填的表）是上次留下的。所以续跑起点要按修复类型选：

| 修复类型 | 续跑起点 |
|---|---|
| L1 纯定位 | 失败节点本身 |
| L2 改了结构 / 顺序 | 回退到该段之前的节点 |
| 涉及前置数据 | 全量重跑 |

## 5. 验证方式由「改了什么」决定

| 改了什么 | 验证方式 | 理由 |
|---|---|---|
| **元素库**（定位） | **从失败节点续跑** | 流程没变，前面步骤的页面状态都还在，续跑就是真实场景 |
| **流程结构**（加/删/换节点） | **整条重跑** | 流程变了前面的假设也变了，续跑"碰巧通过"不等于修好 |

⚠️ 硬边界：**前缀里有外部副作用（已提交订单、已付款、已发消息）不能自动重跑**，否则重复执行。

| 前缀状态 | 改结构后 |
|---|---|
| 只读 / 只填表（未提交） | 自动整条重跑 |
| **已提交 / 已支付 / 已发送** | **不重跑，报人** |

## 6. 变更记录的两处落点

```json
// ① 节点内（人打开流程能看见；`_` 开头的键是元数据，引擎读参数时跳过）
"args": {
  "target": "button:has-text(\"提交订单\")",
  "_heal": {"ts": "...", "from": "#submit", "why": "候选命中 role=button/提交订单", "by": "L1"}
}
```

```jsonl
// ② _meta/<flow>.changes.jsonl（每行一条，可审计）
{"ts":"...","run_id":"r-8821","node":"n5","field":"target","old":"#submit",
 "new":"button:has-text(\"提交订单\")","by":"L1","verified":"pass","snap":"snap-0031"}
```

JSON 不支持注释，所以"给流程加说明"落地为 `_heal` 字段——**schema 里定死：`_` 开头的键是元数据，引擎忽略**。

## 7. 不做录制器，只保留元素拾取

| 不做 | 保留 |
|---|---|
| 注入 JS 抓事件、生成事件流、录制 Agent | **元素拾取器**（点一下页面 → 产出一条元素库条目）|
| 事件流 → 节点的转换逻辑 | 手工 / AI 直接写 JSON |

**为什么砍**：录制的价值是"不用手写流程"，而这件事 AI 直接写 JSON 更快更准；录制还要处理降噪、iframe、埋点参数，七百多行和一堆调参。

**为什么保留拾取**：元素定位（role / name / hints）需要浏览器上下文，且是元素库的唯一入口，不能靠猜。

## 8. 两套定位依据不能混

| | Accessibility tree | CSS selector |
|---|---|---|
| 是什么 | 浏览器**实时算出来**的语义树 | 一段 DOM 查询字符串 |
| 例子 | `role=button, name="提交订单"` | `#submit` / `.btn-primary` |
| 生成条件 | **浏览器必须在跑** | 可离线手写 |
| 稳定性 | 高（改版通常只改样式不改语义）| 低（id / class 常变）|
| 精准度 | 中（同名元素冲突，需限定范围）| 取决于写的人 |
| 速度 | 慢（遍历树）| 快（CSS 引擎直接匹配）|

**结论**：Agent 没连浏览器时只能猜 CSS——这就是"探索走 MCP、回放走引擎"的技术原因。

## 9. 明确不做

| 不做 | 原因 |
|---|---|
| 可视化画布 | JSON + Agent 生成足够 |
| 多机器人集群 / 审批 / RBAC | 平台功能，与"内核"无关 |
| 流程挖掘 / IDP | 用不上 |
| 自研浏览器指纹 | 用 Playwright 现有能力，要更强就上指纹浏览器 |

## 10. 模块分工

```
heal/
  context.py     失败上下文：节点 / 错误 / 候选 / 快照
  rules.py       错误分类（判层）
  agent.py       L1 规则 + L2 LLM 循环（进程内，不经 MCP）
```

**MCP 层应该是全项目最薄的一层**（只有签名和转发）。它变厚说明逻辑漏到了协议层。
